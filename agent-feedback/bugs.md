Out-of-scope defects noticed while working on something else. Format and rules: [README.md](README.md).

## Resolve `config.root` in the Vite plugin's `config` hook — a relative root yields an empty `@marko/run/router`

`packages/run/src/vite/plugin.ts` › `config` | 2026-08-03 | impact:med | effort:low

The `config` hook sets `root = normalizePath(config.root || process.cwd())`, but Vite runs plugin `config` hooks before it resolves the root, so a relative root (`vite --root app`, `root: "./app"` in a `vite.config.ts`, even `root: "."`) is stored verbatim. Virtual modules are then keyed by `path.posix.join(root, ROUTER_FILENAME)` while `resolveId` hands back `path.resolve(root, ROUTER_FILENAME)`, so `virtualFiles.has(id)` misses in `load` and `@marko/run/router` degrades to an empty module: with `root: "./app"` an SSR build fails with `[MISSING_EXPORT] "fetch" is not exported by "app/__marko-run__router.js"`, and in dev `ssrLoadModule("@marko/run/router")` resolves to `{}` where the same project with an absolute root exports `match`/`invoke`/`fetch`. The same hook also builds `optimizeDeps.entries[0]` from `path.relative(root, routesDir)` with the raw option instead of the `resolvedRoutesDir` computed just above, so whenever Vite's cwd differs from the root the glob picks up a `../` prefix and the startup dep scan skips route templates entirely. Resolve once: `root = normalizePath(path.resolve(config.root || process.cwd()))` and `path.relative(root, resolvedRoutesDir)`. The `marko-run` CLI is immune because `packages/run/src/cli/commands.ts` always passes an absolute `root: cwd`; this hits the direct Vite-plugin setup documented under "Vite Plugin" in `packages/run/README.md` and middleware-mode servers.

## Resolve `build.outDir` with `path.resolve` and empty it the way Vite does

`packages/run/src/vite/plugin.ts` › `config` | 2026-08-03 | impact:med | effort:low

The `config` hook computes `outputDir = path.join(root, config.build?.outDir || "dist")`, but `path.join` mangles an absolute outDir, and the CLI's `-o/--output` flows straight into `build.outDir` (`packages/run/src/cli/commands.ts` › `build`). Building with `-o /abs/out` writes the generated route templates to `<root>/abs/out/.marko-run/index.marko` — a mirrored junk tree inside the project whose empty directories outlive the `closeBundle` cleanup — while the real `/abs/out`, which Vite resolves correctly, is never emptied and keeps stale files from previous builds. The `buildStart` cleanup is also far more destructive than Vite's `prepareOutDir`: gated only on `emptyOutDir ?? true`, it runs `fs.rmSync(outputDir, { recursive: true })`, so `build.outDir: "../out"` deletes that entire directory, `.git` and all, before the client pass fails anyway with `vite:build-html` rejecting the `../out/.marko-run/index.marko.html` entry name — whereas Vite refuses to empty an out-of-root outDir when `emptyOutDir` is unset and its `emptyDir` preserves `.git` and the directory itself. Use `path.resolve(root, config.build?.outDir || "dist")` and mirror Vite's `resolveEmptyOutDir`/`emptyDir` semantics instead of `rmSync`; deferring to Vite's own emptying is not a drop-in, since `prepareOutDir` runs at `renderStart`, after the plugin has already written `<outDir>/.marko-run/*.marko`. Related to the existing entry on moving dev's generated route entries out of the build outDir, which shares this `rmSync` but is about where dev entries live.

## Type the `Schema` failure branch as the raw input shape, not the schema's declared `Input`

`packages/run/src/runtime/types.ts` › `Schema` | 2026-08-03 | impact:med | effort:low

`Schema<I, O>` types the validation-failure element as the schema's declared input `I`, but a value that failed validation is by definition not an `I`: `normalizeValidator` (`packages/run/src/runtime/internal.ts`) returns `[input, result.issues]`, where `input` is the raw record the runtime built — `searchParamsToObject(url.searchParams)` for `search`, `route.params` for `params`, the `JSON.parse` result for `json`, and the parsed form record for `form`. Even a correctly input-typed schema breaks: with `search: v.object({ page: v.pipe(v.string(), v.transform(Number)) })`, omitting `?page` yields `{}` and `?page=1&page=2` yields `{ page: ["1","2"] }`, yet both narrow to `{ page: string }` inside `if (issues)`, so the documented "handle the issues, then re-render" path (`packages/run/cheatsheet.md`) crashes on `value.page.length` with no type error. This also contradicts the cheatsheet's own statement that the failure value is the raw input, and nothing encodes the current typing as deliberate — the `request-body-json`/`request-body-form` fixtures bind the failure value as `_body` and assert only on `issues`. Type the failure element from the raw shape instead — `Record<string, string>` for `params`, `Record<string, string | string[]>` for `search` and `form`, `unknown` for `json` — which `Validation<T>` can thread per key since it already maps by option name, and `Schema` has only one internal reference (`Validated`) to update.

## Pass `out` to the crawler in the static adapter's custom-entry branch so prerendered pages land in the build output

`packages/adapters/static/src/index.ts` › `buildEnd` | 2026-08-03 | impact:med | effort:low

In `buildEnd` the default-entry branch constructs the crawler with `out: path.join(path.dirname(builtEntries[0]), "public")`, but the custom-entry branch — the one that spawns `node <builtEntry>` and crawls it over an undici `Pool` — passes only `origin` and `notFoundPath`. `createCrawler` (`packages/adapters/static/src/crawler.ts`) then falls back to `nodePath.resolve(opts.out || "dist")`, a cwd-relative `dist`, so every prerendered page is written outside the client build: `marko-run build src/index.ts` with the static adapter writes the page to `<cwd>/dist/index.html` while `<outDir>/public` is left empty, and with `--output out` the pages still land in `<cwd>/dist`. Since `startPreview` serves `path.join(dir, "public")` and deploys ship `<outDir>/public`, both preview and the deployed site end up with no pages at all. Pass the same `out` in both branches, and add a `static-adapter-*` fixture that sets a custom `entry` — none currently does, so this branch is untested.

## Strip the query string in the static crawler's `resolvePath` so query links stop emitting unservable `?`-named files

`packages/adapters/static/src/crawler.ts` › `resolvePath` | 2026-08-03 | impact:med | effort:low

`resolvePath` returns `url.pathname + url.search`, and `visit` uses that one string both as the `seen` dedup key and as the on-disk target (`nodePath.join(out, path + ".html")`), so an ordinary `<a href="/posts?page=2">` writes `dist/public/posts?page=2.html`. Static hosts strip the query before resolving a file, so those copies are never served: crawling a stub whose root links `/posts`, `/posts?page=2` and `/search?q=hello%20world` emits `index.html`, `posts.html`, `posts?page=2.html` and `search?q=hello%20world.html`, and serving that directory through the adapter's own sirv config (`startPreview` in `packages/adapters/static/src/index.ts`) answers `/posts?page=2` from `posts.html` and 404s `/search?q=hello%20world`. Worse, a dynamic route reachable only through a query link — root linking `/users/123?tab=posts`, which `buildEnd` does not seed as a param-free path — emits `users/123?tab=posts.html` and no `users/123.html` at all, so the page is simply missing from the build; the query variant also re-renders a route already crawled at its bare path, and `?` is an illegal filename character on Windows, where the write fails outright. Strip `search` in `resolvePath` so query variants collapse onto the already-seen pathname, or keep `search` only in the `seen` key and derive `filePath` from `url.pathname` alone (`resolvePathWithHash` keeping `search` is separate and correct, since it builds the browser-facing meta-refresh URL). No `static-adapter-*` fixture links a query string.

## Emit the prerendered 404 as `404.html` under trailing-slash modes, not `404/index.html`

`packages/adapters/static/src/crawler.ts` › `visit` | 2026-08-03 | impact:med | effort:low

With `trailingSlashes: "RedirectWith"` or `"RewriteWith"`, `buildEnd` in `packages/adapters/static/src/index.ts` passes `notFoundPath: "404/"`, but `visit()` computes `filePath` _before_ `switch (res.status)`, so the `case 404:` trailing-slash trim (`path = path.slice(0, -1)`) no longer affects the output path — after the switch `path` is only read by the `path !== notFoundPath` guard inside `if (redirect)`, which a 404 never reaches. Building an app with `trailingSlashes: "RedirectWith"` and a `+404.marko` emits `dist/public/404/index.html` and no `dist/public/404.html`, while the same app in the default mode emits `dist/public/404.html`. Static hosts (Netlify, GitHub Pages, Cloudflare Pages) key their error page off a root `404.html`, so those deploys serve the host's generic 404 instead of the app's `+404` page. Recompute `filePath` inside the `case 404:` branch after the trim (or move the assignment below the switch while keeping the `case 200:` non-HTML override) so the error page always lands at `<out>/404.html`. Nothing catches it: the `static-adapter-trailing-slash` fixture has no `+404` route, and `startPreview`'s sirv config resolves `/404` to `404/index.html` as readily as to `404.html`.

## Stop silently dropping a grave-escaped literal that starts a flat route pattern

`packages/run/src/vite/routes/parse.ts` › `parseFlatRoute` | 2026-08-03 | impact:med | effort:low

In `parseFlatRoute` the `CharCodes.Directory` branch flushes only `if (current)` and then clears `escaped`, so a grave-escaped literal that opens a pattern is thrown away as soon as the next `.` arrives — the `,` branch and the end-of-pattern flush both honor `escaped`, which is why a lone `` `sitemap.xml` `` directory correctly yields `/sitemap.xml`. Running `buildRoutes` over `` `sitemap.xml`.rss/+handler.ts `` produces `/rss`, and over `` `.well-known`.security`.`txt+handler.ts `` produces `/security.txt`: the route silently mounts at a path the author never wrote, with no error or warning. Escaping a dotted directory and then nesting under it in the same flat name is exactly what the README's "Escaping Control Characters" section leads people to write, and the unescaped spelling is no better — `src/routes/.well-known/security.txt/` quietly becomes `/well-known/security/txt`. Seeding `current` from `basePaths` when `escaped` is non-empty before the Directory flush repairs both shapes without changing any documented behavior; `packages/run/src/vite/__tests__/parse-flat-route.test.ts` has no case for an escape at the start of a pattern.

## Write a 500 status instead of destroying the socket when the middleware has no `next`

`packages/run/src/adapter/middleware.ts` › `createMiddleware` | 2026-08-03 | impact:med | effort:low

When `createMiddleware` catches an error and the caller passed no `next`, the whole recovery is `res.socket?.destroySoon()` plus a `console.error` — no status line is ever written, so the client gets a zero-byte reply. That is the shipped production path: `packages/run/src/adapter/default-entry.mjs`, the default entry for the base adapter and `@marko/run-adapter-node`, invokes `middleware(req, res)` with no third argument. The generated router's `fetch` catches its own errors and returns a bare 500, but everything raised outside it still lands in this branch — `getOrigin` throwing when a request carries no `Host` header and `NODE_ENV` is production, `copyResponseHeaders` throwing `headers is not iterable` when a `+handler` returned a non-`Response`, and a page-render stream that errors before its first chunk — and in all three the response is still unflushed, so proxies and load balancers see a bodiless close, record no status, and may retry a non-idempotent request. In that branch, when `!res.headersSent && !res.destroyed`, drop the headers already copied over, set `res.statusCode = 500` and call `res.end()`, and reserve `destroySoon()` for the already-flushed case where truncating the chunked body is the correct signal.

## Build the `context.body` thenable whenever a `json`/`form` option is configured, not only when the request carries a body

`packages/run/src/runtime/internal.ts` › `createContext` | 2026-08-03 | impact:low | effort:low

`createContext` attaches the body thenable only when the incoming request actually carries one — `route && request.body && (route.options.json || route.options.form)` — so a `POST`/`PUT`/`PATCH` whose `Request.body` is `null` leaves `context.body` as `undefined`. Both the type and the docs promise otherwise: `RouteForFileDef["body"]` in `packages/run/src/runtime/types.ts` resolves to `Promise<...>` with no `| undefined` once a `json`/`form` validator is merged in, and `packages/run/README.md` ("Request Bodies") states that when either option is configured `context.body` is a promise for the parsed body, so the documented `const [data, issues] = await context.body` throws `TypeError: (intermediate value) is not iterable` and 500s. The node adapter masks this because `createMiddleware` always attaches the `IncomingMessage` as the body for those verbs, but a bodyless `context.fetch(path, { method: "POST" })` subrequest, or a hand-built `Request` passed to `Run.fetch`/`Run.invoke` as the README's Express recipe shows, reaches it. Drop the `request.body` condition so a configured validator always yields a thenable — `readBodyWithLimit`'s `throw new Error("Missing request body")` then needs the 400 treatment tracked by the existing "Return 400/413 instead of 500" entry — or widen `RouteForFileDef["body"]` and the README to `| undefined`.

## Relax the `Route` and `GetUpstreamData` type-parameter constraints so `@marko/run`'s own declarations type-check against generated route types

`packages/run/src/runtime/types.ts` › `Route` | 2026-08-03 | impact:low | effort:low

Once an app's generated `.marko-run/routes.d.ts` (`interface App extends $.DefineRoutes<...>`, emitted by `packages/run/src/vite/codegen/index.ts`) is in the TS program, `@marko/run`'s own declarations stop satisfying their type-parameter constraints and `tsc` reports three TS2344 errors inside `packages/run/src/runtime/types.ts` (shipped as `dist/runtime/types.d.ts`) that no app-side change can silence. Two come from `Route`'s `Def extends RouteDef` constraint: the default `RouteDef` has `Options = unknown`, so its `form`/`json` collapse to `never`, while every def `DefineRoute` builds passes `RouteOptionsContainer<Path, Verb>`, leaving `form` a deferred conditional TS cannot reduce to `never` — so `ContextForPath` and `ContextForFile` both violate the constraint on their `Route<...>` instantiations, even for an app that declares no validators. The third comes from `RouteForFileDef` passing its `Path extends keyof AppPaths` into `GetUpstreamData<F, Path extends PathsForFile<F>, Verb>`. Consumers only hit these with `skipLibCheck: false`, but that is a legitimate setting and the errors originate entirely inside the package. Widening the two constraints to `Def extends RouteDef<string, HttpVerb, any, any, any>` and `Path extends PropertyKey` (`GetUpstreamData` already re-guards internally with `Path extends keyof AppPaths ? … : Empty`) clears all three and leaves `ctx.params`, `ctx.method`, `ctx.body` and middleware-derived `ctx.data` resolving identically.

## Keep a literal `/404` or `/500` route from colliding with the `+404`/`+500` entry templates

`packages/run/src/vite/routes/builder.ts` › `buildRoutes` | 2026-08-03 | impact:low | effort:low

`buildRoutes` gives the root `+404.marko`/`+500.marko` pages `key: type` and `templateFilePath: <entryFilesDir>/404.marko`/`500.marko`, but never seeds those keys into the `seenKeys` set used to de-dup regular route keys, so a literal `src/routes/404/+page.marko` computes the same key and is handed the identical entry-template path. `renderVirtualFiles` in `packages/run/src/vite/plugin.ts` writes `routes.list` templates first and `routes.special` templates second, so the special page always wins: on a tree with `+404.marko`, `+500.marko`, `404/+page.marko` and `500/+page.marko`, `marko-run dev` answers `GET /404` and `GET /500` with 200 and the special pages' markup instead of the real route pages, and nothing warns. The `route.key === RoutableFileTypes.Error` test in `renderRouteTemplate` (`packages/run/src/vite/codegen/index.ts`) compounds this — any `src/routes/500/+page.marko` is emitted as `<Page error=input.error/>` even when no `+500.marko` exists. Seed `seenKeys` with `RoutableFileTypes.NotFound`/`Error` before `traverse` runs so a colliding route falls back to key `4042`/`5002`, and drive the error-input decision off an explicit flag on `Route` instead of comparing `key`. No fixture under `packages/run/src/vite/__tests__/fixtures` covers a `404`/`500` route directory.

## Reject route files nested under a `$$` catch-all directory instead of letting them hijack the router

`packages/run/src/vite/routes/vdir.ts` › `VDir.addPaths` | 2026-08-03 | impact:low | effort:low

`src/routes/$$rest/foo/+page.marko` is accepted even though `packages/run/README.md` states that catch-all directories cannot nest route files and are not traversed further, and `parseFlatRoute` (`packages/run/src/vite/routes/parse.ts`) throws "nested segments are not allowed after a catch-all parameter" for the equivalent flat form `$$rest.foo+page.marko`. `buildRoutes` parses each directory name in isolation and `VDir.addPaths`/`addDir` never check whether the parent's segment is `$$`, so the route is built with `segments: ["$$", "foo"]`; `createRouteTrie` (`packages/run/src/vite/codegen/index.ts`) then returns at the first `$$`, and the emitted router makes that page the root fall-through — `/` and every path not claimed by a static or dynamic sibling returns `{ path: '/$$rest/foo', params: { rest: pathname.slice(1) } }`, silently discarding the `/foo` the author wrote. If a sibling `src/routes/$$rest/+page.marko` exists, `catchAll ??=` keeps the first insert and `/$$rest/foo` disappears from the router entirely while `renderRouteTypeInfo` still declares it, so `Run.href("/$$rest/foo", { params: { rest: "a" } })` type-checks against an unreachable route and returns `"/undefined"`. Mirror the parse-time error in the builder: throw from `VDir.addDir`/`addPaths` when a segment is added under a dir whose own `segment.type === "$$"` — check the parent segment rather than the source `Path.isCatchall` flag, which belongs to the whole flat expansion and would falsely reject the legal dir name `a.$$rest` — or wire up the `onDir` hook that `packages/run/src/vite/routes/walk.ts` declares and `buildRoutes` never passes.

## Key catch-all dirs by their raw name so sibling `$$a`/`$$b` error instead of silently merging

`packages/run/src/vite/routes/vdir.ts` › `VDir.addDir` | 2026-08-03 | impact:low | effort:low

`VDir.addDir` keys child directories with `segment.type === "$" ? segment.raw : segment.name`, and `segmentEnd` in `packages/run/src/vite/routes/parse.ts` rewrites every catch-all's `name` to the literal `"$$"`, so sibling catch-alls with different param names collapse into one `VDir` while sibling `$` dirs stay distinct. `src/routes/$$a/+middleware.ts` beside `src/routes/$$b/+page.marko` builds a single route with `path.path === "/$$a"` and `params === { a: null }`, silently serving `$$b`'s page under `$$a`'s param name — `params.b` is `undefined` and the generated route types declare `a` — and a `$$b/+handler.ts` or `+meta` is hoisted onto `$$a`'s route the same way; the flat form merges identically since `onFile` goes through the same `addPaths`/`addDir`. Only same-type collisions surface at all, as `addFile`'s `Duplicate file type page added at path /$$`, whereas the `$` analogue is always loud: `buildRoutes`' `uniqueRoutes` check throws `Duplicate routes for path /$`, snapshotted in `packages/run/src/vite/__tests__/fixtures/error-invalid-routes`. The raw-keying for `$` was added specifically to stop this kind of param-name merge and `$$` was left out, so widen the key to `segment.type === "$" || segment.type === "$$" ? segment.raw : segment.name` and let a sibling catch-all collision throw `Duplicate routes for path /$$`.

## Append the dev client-id cookie instead of overwriting `set-cookie` on the response

`packages/run/src/adapter/dev-server.ts` › `getDevGlobal` | 2026-08-03 | impact:low | effort:low

`getDevGlobal`'s `onClient` writes its correlation cookie with `res.setHeader("set-cookie", ...)`, and `createMiddleware` (`packages/run/src/adapter/middleware.ts`) calls it as the first statement of every `text/html` request whenever `NODE_ENV` is unset or `development` and `globalThis.__marko_run_dev__` exists. Because `setHeader` replaces the whole header, any `Set-Cookie` an upstream Connect/Express middleware already queued on `res` is silently dropped: with `@marko/run-adapter-node`'s `routerMiddleware` mounted after a middleware that does `res.cookie(...)` then `next()` — the layout the node adapter README documents, and the one `ensure-runtime.ts` installs the dev global for — the upstream cookie never reaches the browser in dev, while the same server works in production where `onClient` is skipped. The adapter already handles this correctly in the other direction: `copyResponseHeaders` special-cases `set-cookie` to `appendHeader`, pinned by `packages/run/src/__tests__/adapter-middleware.test.ts` › "should preserve existing cookies set". Switch `onClient` to `res.appendHeader("set-cookie", ...)`, which sets the header when none exists and leaves upstream cookies intact.

## Send the dev worker's entry-load error to `ws.send` as an object so Vite delivers it as an `error` payload

`packages/run/src/adapter/load-dev-worker.mjs` › `start` | 2026-08-03 | impact:low | effort:low

## Handle explorer build failures instead of crashing the explorer worker on the first request

`packages/explorer/lib/server.js` › `build` | 2026-08-03 | impact:low | effort:low

`build()` calls `reject(error)` without returning, so a failed `marko-run build` falls straight through to `await import(<appDir>/index.mjs)` — a file that does not exist precisely because the build failed — and the async `exec` callback rejects a second time with nothing attached to catch it. The lazy `middleware = (req, res) => { build().then(() => middleware(req, res)) }` also attaches no `catch`, so the first rejection is unhandled as well. Under Node's default `--unhandled-rejections=throw` either one kills the forked explorer worker (`spawnServerWorker` via `startExplorer` in `packages/run/src/adapter/index.ts`): with `marko-run` missing from the exec'd shell's `PATH`, or the install dir read-only, the very first request gets an empty reply, the explorer URL printed by `logInfoBox` is dead for the rest of the session, and all the user sees is a raw V8 stack in the dev output. Return after `reject`, `catch` in the middleware and reply 500 with the captured build output, and reset `buildPromise` on failure so the next request retries instead of replaying the cached rejection.

## Write the crawled 404 page only for the 404 path itself, not for every path that answers 404

`packages/adapters/static/src/crawler.ts` › `visit` | 2026-08-04 | impact:med | effort:low

With a `+404` route the adapter passes `notFoundPath`, and `visit`'s `case 404:` then breaks out of the switch for _any_ path that answered 404, so the 404 page's own markup is written to `<out>/<path>.html` for each one. A link to a page that no longer exists therefore ships as a real file: a fixture whose page links `/gone` emits `dist/public/gone.html` containing the `+404.marko` markup, and driving the adapter's own `startPreview` over that build answers `GET /gone` with `200` and the not-found markup (verified; static hosts resolve `/gone` to that file the same way). That is a soft 404 — clients, caches and search crawlers see a success at a URL that does not exist, and the host never falls back to the root `404.html` it would otherwise serve with a real 404 status. Write the page only when `path === notFoundPath` (the seeded 404 route) and treat every other 404 the way the pre-`notFoundPath` branch already does — abort and write nothing — which `crawl`'s summary now reports under "Paths that answered 404" either way.

## Answer an unknown path in static preview with the 404 body, not a redirect to `/404`

`packages/adapters/static/src/index.ts` › `startPreview` | 2026-08-04 | impact:low | effort:low

`startPreview`'s sirv fall-through answers any path that matched no file with `res.writeHead(302, undefined, { location: "/404" })`, so preview reports a not-found URL as a redirect to a page that answers 404, while every static host the adapter targets answers 404 at the requested URL itself. A test or crawler asserting that an unknown URL 404s sees the 302 first, and preview is the one place that shape can be caught before deploy. Serve `404.html`'s body from the fall-through with an explicit `res.writeHead(404)` rather than redirecting to a path that exists in the build output. The `/404` page's own status is no longer part of this -- `forceStatus` pins it around sirv, which is what sirv's `setHeaders` could not do.

## Routes 404 after Vite's in-place restart when the config graph changes

`packages/run/src/vite/plugin.ts` › `virtualFiles` | 2026-08-10 | impact:med | effort:med

If `vite.config.ts` imports project source (e.g. to start a sidecar server from `configureServer`), editing any file in that import graph makes Vite restart in place — and after that restart every route answers 404 until the whole `marko-run dev` process is killed and restarted. Observed repeatedly in a real app; the workaround was spawning the sidecar as a child process (`spawn(process.execPath, [entry])`) so the config graph never touches server code, plus explicit `.ts` extensions to keep imports out of the graph. Suspect the `virtualFiles` map / route-walker state is not rebuilt on Vite's in-place restart path the way it is on first boot. ## Dev server drops WebSocket upgrades: `server.proxy` ws entries never connect, unmatched upgrades answer 404

`packages/run/src/adapter/dev-server.ts` › `createViteDevServer` | 2026-08-10 | impact:high | effort:med

Dev runs Vite in middleware mode behind marko-run's own listener (`devServer.middlewares.listen` in `startDev`, `packages/run/src/adapter/index.ts`), so `server.httpServer` is `null` inside every Vite plugin and no upgrade path exists. Three verified consequences for an app that serves its own WebSocket: (1) a user config `server.proxy: { "/term": { target: "ws://localhost:7172", ws: true } }` completes the client handshake but never establishes the upstream — the socket opens, receives zero frames, and dies with 1006, silently; (2) without the proxy entry, an upgrade request for an app path is processed as a plain request and the router writes an HTTP 404 to the wire (a `ws` client reports "Unexpected server response: 404"); (3) a plugin cannot work around it, since `configureServer` never sees the real http server. Direction: hand the listener to Vite (`server.hmr.server`) and honor `server.proxy` ws entries against it — the same listener the existing HMR-port entry needs. Until then the only workaround is fronting the dev server with an external path-routing proxy. Re-verify: `marko-run dev` app with that proxy config, `new WebSocket("ws://localhost:<port>/term/x")` — open then 1006 with no upstream traffic; remove the proxy entry and the handshake gets 404.

## Any middle segment makes a file a route, so `+handler.test.ts` registers as a second handler

`packages/run/src/vite/routes/builder.ts` › `RoutableFileRegex` | 2026-08-14 | impact:med | effort:low

`nonMarkoFiles` (and `markoFiles`) allow an arbitrary middle segment — `(+middleware|+handler|+meta)\.(?:.*\.)?(.+)` — and nothing ever reads that group (`matchRoutableFile` and `onFile` only use the type and the trailing extension).
