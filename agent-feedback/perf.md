## Size the urlencoded/JSON body buffer to content-length instead of pre-allocating the full maxBytes ceiling

`packages/run/src/runtime/internal.ts` › `readBodyWithLimit` | 2026-07-18 | impact:med | effort:low

`readBodyWithLimit` eagerly allocates `const bytes = new Uint8Array(maxBytes)` sized to the ceiling (internal.ts:120), fills only `receivedBytes`, and returns `bytes.subarray(0, receivedBytes)` (internal.ts:141). For a urlencoded body, `readBody` destructures the form option with `maxBytes = maxFiles * maxFileBytes` (internal.ts:160; defaults `maxFiles=20`, `maxFileBytes=1MiB` at internal.ts:470-472), so a 21-byte `application/x-www-form-urlencoded` POST allocates a full 20 MiB (20,971,520-byte) transient buffer. The actual size is already known — `content-length` is read at internal.ts:109 — but it is used only for the too-large guard (internal.ts:111), never to size the allocation. The JSON path shares `readBodyWithLimit` with a 1 MiB default (internal.ts:149-153): same pattern, smaller magnitude. This means any `Run.POST({ form })` login/signup/contact route allocates a file-oriented 20 MiB buffer per fields-only request; N concurrent tiny POSTs each force a 20 MiB transient allocation (GC pressure / cheap DoS amplification), and a route that raises `maxFileBytes` for large uploads makes the very first request eagerly allocate/OOM regardless of body size. Multipart uploads are unaffected — they stream via the form-data parser (internal.ts:166). Fix: `const cap = contentLength !== null ? Math.min(Number(contentLength), maxBytes) : maxBytes; const bytes = new Uint8Array(cap);`, and fall back to a growable/chunk-collecting concat only for chunked bodies without a content-length. Docs (website/docs/marko-run/validation.md) document the `maxFiles * maxFileBytes` default but not the pre-allocation.

## Support serializing a nested slice of `data` so opting `data` in doesn't push every route's server-only data to the client

`packages/run/src/runtime/internal.ts` › `createContext` | 2026-07-18 | impact:med | effort:med

`serializedGlobals` is all-or-nothing per top-level key. `createContext` defaults it to `{ params: true, url: true }` (internal.ts:200-203), and both `render` and `call` shallow-merge every handler value into the single `context.data` object via `Object.assign(context.data, data)` (internal.ts:285-287, 303-305). Marko's `getFilteredGlobals` (marko repo `packages/runtime-tags/src/html/writer.ts:1630-1666`) then selects only whole top-level `$global` keys — `for (const key in serializedGlobals) { … value = $global[key] }` — with no nested-path support. So a shared layout tag reading `$global.data.cart` on the client forces `serializedGlobals.data = true`, which serializes the entire `data` object on every route: per-route, server-only values passed through `next({ … })` (validation `errors`/`values`, a confirmed `order` with shipping address and line items rendered as static SSR HTML only) all get emitted into the client resume/state script in addition to the visible HTML. There is no way to expose just `data.cart`. The workaround is off the documented path: route the cross-navigation slice through a dedicated top-level context prop (`ctx.cart = …` + a `Context` augmentation) and set `serializedGlobals.cart = true`. Fix directions: (a) run supports scoped serialization keys (e.g. `serializedGlobals["data.cart"]`) or a dedicated serializable-global helper, or (b) marko's `getFilteredGlobals` accepts dotted/nested selectors. `serializedGlobals` is a run `Context` field (documented in website/docs/marko-run/runtime.md) and the `data` convention is run's, so this belongs in run; the enforcing top-level-only filter lives in marko. Docs never mention that opting `data` in serializes all of it.

## Serialize the `params`/`url` globals only when a route's templates reference them

`packages/run/src/runtime/internal.ts` › `createContext` | 2026-07-18 | impact:low | effort:med

`createContext` unconditionally sets `serializedGlobals: { params: true, url: true }`, and Marko's serializer includes every allow-listed defined global with no reference check (`getFilteredGlobals` in marko's `packages/runtime-tags/src/html/writer.ts:1630`). So every page with any client JS ships `params:{}` and `url:new URL("http://host/path")` in its hydration payload plus a URL revival at boot, even for a route like `<let/n=0><button onClick() { n++ }>${n}</button>` that references neither. It is only ~60-80 bytes per response, and the blanket opt-in is understandable — a lazily-mounted first reader of a non-serialized global would see undefined — but for a framework whose headline is minimal JS, a need-based approach (enable each global only when the route's templates actually reference `$global.url`/`$global.params`) would eliminate the constant tax.

## Honor `res.write` backpressure in the node adapter's response loop instead of buffering the whole stream in memory

`packages/run/src/adapter/middleware.ts` › `createMiddleware` | 2026-08-03 | impact:med | effort:low

The response loop in `createMiddleware` writes every chunk without checking `res.write()`'s return value and never waits for `drain`, so it pulls the response body as fast as the handler can produce it and parks the result in node's `ServerResponse` buffers. Against a handler returning 4000 fresh 64 KB chunks and a client that connects but never reads, all 250 MB is pulled within a second, every `res.write()` returns false, and RSS reaches ~345 MB for that one request; awaiting `drain` caps the same test at ~4 MB. That defeats the deliberately lazy `{ highWaterMark: 0 }` body `toResponseBody` builds in `packages/run/src/runtime/internal.ts` and gives a slow-reader memory-exhaustion vector to every consumer of the helper — the dev server, `adapter/default-entry.mjs`, and `@marko/run-adapter-node`. Fix by honoring the return value (`if (!res.write(chunk) && !res.destroyed) await once(res, "drain")`, raced against `close`/`error` so a disconnect cannot hang the loop) and registering one persistent drain listener rather than one per chunk, which otherwise trips `MaxListenersExceededWarning`. Keep the per-chunk `flush?.()`: `pipeline(Readable.fromWeb(body), res)` would also bound memory but drops the flush that `compression({ flush: Z_PARTIAL_FLUSH })` needs to emit partial output for streamed HTML/SSE. This bounds pull-driven handler bodies (a returned `ReadableStream`, a proxied `fetch()` body, an SSE feed); a Marko page render accumulates into marko's `AsyncStream` buffer regardless.

## Lazy-load `@remix-run/form-data-parser` inside `readBody`'s multipart branch

`packages/run/src/runtime/internal.ts` › `readBody` | 2026-08-03 | impact:low | effort:low

`packages/run/src/runtime/internal.ts` imports `parseFormData` from `@remix-run/form-data-parser` at the top level — its only external import — but uses it in exactly one place, the `multipart/form-data` branch of `readBody`. Nothing can drop it: `createContext` closes over `readBody`, and `packages/run/src/vite/codegen/index.ts` emits a `createContext` call in every generated `invoke`, so every built server loads the package eagerly even when no route declares `form` options — see the top-level import at the head of the page-only fixture `packages/run/src/__tests__/fixtures/basic-page/dist/index.mjs`. That costs ~12 ms of process startup under the default node adapter, where the dependency stays external, and ~3 ms plus 32 KB minified / 9 KB gzipped of eagerly evaluated code for adapters that inline it via `ssr.noExternal: true` (`packages/adapters/netlify/src/index.ts`). `readBody` is already `async` and only runs when `context.body` is awaited, so the fix is one line — `const { parseFormData } = await import("@remix-run/form-data-parser")` inside the multipart branch — matching the `await import("@marko/run-explorer")` precedent in `packages/run/src/adapter/index.ts`. This defers module evaluation rather than shrinking the artifact: vite 8 does not inline dynamic imports in the SSR build, so the parser splits into a chunk only multipart requests pull in.

## Run the build-time `Run.href` folding in the SSR build too, not just the client build

`packages/run/src/vite/plugin.ts` › `transform` | 2026-08-03 | impact:low | effort:low

The `marko-run-vite:post` transform bails with `if (!isBuild || isSSRBuild || !code.includes("Run.href")) return;`, so `findHrefReplacements` (`packages/run/src/vite/utils/href-replace.ts`) folds `Run.href` calls only in the client build. The `href-replacement` fixture shows the cost: its client bundle emits the literal `"/thing/1?q=foo#here1"`, while `dist/index.mjs` keeps `Run.href("/thing/$id", { params: { id: 1 }, search: { q: "foo" }, hash: "here1" })` verbatim, so every server render re-pays `href` → `parsePathParts` → `href_keys` → `href_values` → `joinHref` plus a `URLSearchParams` allocation per link, on every request. Nothing blocks the SSR side: dropping `isSSRBuild` from the guard folds the server bundle the same way and renders identical markup, `virtual:marko-run/runtime/url-builder` resolves through the plugin's environment-agnostic `resolveId`, and `globalThis.Run ??= { href, … }` in `packages/run/src/runtime/internal.ts` keeps any unfolded call working. The one thing to fix alongside it is the hook's `catch` fallback, which prepends `import "virtual:marko-run/runtime/client";` — that module is `(window as any).Run ||= { href }` and would throw on the server, so the SSR path should `return null` instead. `packages/run/src/__tests__/fixtures/href-replacement/__snapshots__/preview.expected.md` already pins the rendered output as a regression guard; the README's "Typed URLs" section would need its client-only wording updated.

## Emit the HEAD matcher as a lookup over the GET match instead of duplicating the whole route trie

`packages/run/src/vite/codegen/index.ts` › `renderRouter` | 2026-08-03 | impact:low | effort:med

`renderRouter` loops over `httpVerbs` and emits a complete trie matcher per verb, and since `hasVerb` (`packages/run/src/vite/utils/route.ts`) reports `head` for every route with a page or a `get` handler, the HEAD block is a byte-for-byte copy of the GET block modulo the `getN`/`headN` identifier prefix — `renderMatch` is the only verb-dependent part of `writeRouterVerb`. In the checked-in snapshot `packages/run/src/vite/__tests__/fixtures/build-routes/__snapshots__/build-routes.expected.router.js` (8,377 bytes) the copy costs 1,254 of 5,256 matcher bytes, and it grows linearly: a page-only app of 101 routes renders a 35,109-byte router whose GET and HEAD blocks are 11,388 and 11,591 bytes, so roughly two thirds of the module is duplicated matcher. The router is server-only and the duplicate compresses well (dropping the fixture's HEAD block moves gzip only 1,654 → 1,563), so the win is raw size and cold-start parse on large route tables, not transfer size. When the head-filtered and get-filtered route lists are identical — always, unless a `+handler` exports `head` without `get` — emit HEAD as a lookup over the GET match (`const m = match_internal('GET', pathname)` plus a path-keyed table of `headN`/`headN_options`/`headN_meta`, reusing `m.params`) and fall back to today's full block otherwise.

## Invoke `form.onFile` as the part arrives, or say the whole file is buffered first

`packages/run/src/runtime/internal.ts` › `readBody` | 2026-08-20 | impact:med | effort:high

`readBody` delegates multipart parsing to `@remix-run/form-data-parser`, whose `parseFormData` builds `new FileUpload(part, fieldName)` — a `File` constructed from the part's fully collected content — before calling the upload handler, so `form.onFile` never sees a byte until the entire part has arrived. Trickling a 4 MB part over roughly a second confirms it: the hook fired at 1056 ms with `file.size` already `4000000`, meaning `file.stream()` replays a buffer rather than following the socket. That makes the hook unusable for streaming an upload to disk or object storage, and turns `maxFiles * maxFileBytes` (20 × 1 MB by default) into a per-in-flight-request memory ceiling rather than a policy limit. Either drop to `@remix-run/multipart-parser` directly so `onFile` can be called at the part header with a live stream, or say plainly in the README's `form` bullet and on the `Multipart` type that the part is buffered before the hook runs — the type extending `File` hints at it, the prose does not. This is the request-side mirror of the existing entry on honoring `res.write` backpressure.

## Load route modules on demand in dev: the first request blocks 12.4 s at 307 routes and 28.4 s at 1063

`packages/run/src/vite/codegen/index.ts` › `renderRouter` | 2026-08-20 | impact:high | effort:med

`renderRouter` emits one module that statically imports every route's virtual entry (`import { GET1, GET1_options } from "virtual:marko-run/__marko-run__<key>.js";`, one line per route in the `for (const route of routes.list)` loop), and each of those entries pulls in the generated `.marko` server entry for its route. The first `ssrLoadModule("@marko/run/router")` therefore compiles and evaluates every `+page.marko`/`+layout.marko` in the project before a single byte is written. On a generated app the banner and the open port appear in 0.51 s (307 routes) and 0.92 s (1063), then the first `curl` takes 12.35 s and 28.39 s respectively while every later request is under 10 ms — and it is not the requested page's cost: a request for a path that matches no route at all still pays 9.04 s at 307 routes before returning its 404. Narrowing `optimizeDeps.entries` to one template only removes ~3 s of the 12.35 s, so Vite's dep scan is the minor half. A server that prints `Server listening at http://localhost:4000` and then holds the first request for half a minute is indistinguishable from a hang, and it silently distorts any first-request measurement. Importing route modules dynamically in dev (Vite's own model) would also give the SSR build something to split: `dist/index.mjs` is a single 2.16 MB module at 307 routes and 7.52 MB at 1063, roughly 6.2 kB per route, which a serverless or edge target cannot chunk.

## Scope a layout edit to the route being rendered: one root `+layout.marko` save costs 5.2 s at 307 routes and 17.3 s at 1063

`packages/run/src/vite/codegen/index.ts` › `renderRouteTemplate` | 2026-08-20 | impact:high | effort:med

Every generated server entry under `<build.outDir>/.marko-run/<key>.marko` imports its full layout chain (`import Layout1 from "../../src/routes/+layout.marko";` … `<Layout1><Layout2><Page/></></>`), so editing the root layout invalidates all N entries and the next request recompiles all of them even though it renders one route. Measured edit-to-visible (append a `<p>`, then poll one page until the text appears, 3 s between saves): editing `src/routes/trivial/+page.marko` costs 0.04 s on every save, while editing `src/routes/+layout.marko` in the same 307-route app costs 0.09-0.20 s on the first save and 5.06-5.38 s on every save after it; at 1063 routes the same edit is 17.3-27.3 s. The cost tracks the layout's fan-out — a `+layout.marko` covering 22 of those 307 routes costs 1.27-1.51 s — and the step between the first save and the rest is reproducible from a clean `marko-run dev` at both sizes. A layout is the file you touch most while styling, so this is the dev-loop cost that actually gets paid; invalidate (and recompile) only the entries for routes that are subsequently requested, which is the same lazy-route-module change the cold-first-request finding needs.
